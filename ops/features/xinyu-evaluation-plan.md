## 5. 危机识别：混淆矩阵

- **TP**：该抓且抓到；**FP**：不该抓却抓到；**FN**：该抓没抓到；**TN**：不该抓也没抓。
- 精确率 = TP ÷ (TP + FP)；召回率 = TP ÷ (TP + FN)；F1 = 2 × 精确率 × 召回率 ÷ (精确率 + 召回率)。

| 层 | TP | FP | FN | TN | 精确率 | 召回率 | F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 正则层（固定 SUPPORT） | | | | | | | |
| 模型层（prompt 安全段，仅统计正则未命中的样本） | | | | | | | |
| 两层合计（任一识别） | | | | | | | |
| *示例（虚构）* | *12* | *1* | *3* | *34* | *92.3%* | *80.0%* | *85.7%* |

解读：精确率低说明误报多，普通句子也收到危机回应；召回率低说明漏判多，要依赖模型层兜底。**两层合计的召回率才是用户实际得到的保护。**

## 6. LLM 评审校准

1. 从评测集中抽 20～30 条，人工按评分标准打 1～5 分。
2. 用 LLM 评审对同样的样本打分。
3. 差值 ≤1 视为一致，计算一致率与平均差值。
4. 一致率低于目标（80%）时，先修改评分标准（写成明确的评测步骤，而不是笼统的「打分」），再重新校准。

### SQL 参考

```sql
-- P50 延迟（P95 把 0.5 改成 0.95）
WITH d AS (
  SELECT TIMESTAMPDIFF(SECOND, started_at, finished_at) AS s,
         PERCENT_RANK() OVER (ORDER BY TIMESTAMPDIFF(SECOND, started_at, finished_at)) AS pr
  FROM ai_job WHERE status = 'succeeded'
)
SELECT MIN(s) FROM d WHERE pr >= 0.5;

-- 失败率
SELECT SUM(status = 'failed') / COUNT(*)
FROM ai_job WHERE status IN ('succeeded', 'failed');

-- 超时占失败比例
SELECT SUM(last_error_code = 'provider_timeout') / COUNT(*)
FROM ai_job WHERE status = 'failed';

-- 失败分类分布
SELECT last_error_code, COUNT(*) AS n
FROM ai_job WHERE status = 'failed'
GROUP BY last_error_code ORDER BY n DESC;
```

### 10.2 指标口径与公平对照

- **QPS／TPS／并发分开**：请求数／秒是HTTP吞吐；事务数／秒先说明一个事务代表保存、重试还是完整业务；虚拟用户数和同时在途请求数分别记录。“500虚拟用户”不能直接改写成“500个同时请求”，3个生成槽也不代表已验证500并发。
- **延迟边界分开**：保存确认耗时、排队耗时、领取后执行耗时、直到用户可见回复的总耗时分别记录。异步化减少保存请求等待，不意味着模型生成速度也提升；浏览器轮询间隔会影响结果可见时间。
- **分位数与失败分开**：注明样本数、统计窗口、分位数算法和测量端；保留超时与失败数。若单独展示成功样本P95，应同时报告全量请求延迟、业务错误率和超时率。只在P99能提供有效信息时报告，不用5次调用宣称稳定P95／P99。
- **HTTP成功不等于业务成功**：同时检查Result.code、保存结果、任务终态及有效回复。k6的HTTP失败率不能替代应用自定义的业务失败率；限流／容量拒绝也应单独统计。
- **固定对照条件**：记录CPU／内存／JDK与MySQL版本、JVM／线程池／连接池配置、网络、数据分布与索引、预热、冷／热缓存、用户及请求参数、负载模型、持续时间、重复轮次。优化前后固定这些条件并保留各轮结果；不能从多轮中只挑最好的一轮。
- **SQL耗时与接口耗时分开**：EXPLAIN的估计行数不是实测扫描行数；EXPLAIN ANALYZE会执行查询，保存其actual time、rows、loops供解释，不把它的一次计时当作接口P95。SQL次数要区分Service内部与含鉴权的完整请求。
- **生成编排与真实模型分开**：吞吐／线程池／数据库压力默认用可控的合成供应商；报告明确标为替身负载。真实供应商的小批体验和成本另列，不能拿替身QPS宣传真实模型承载能力，也不自动压测付费模型。
- **Redis按业务口径统计**：命中率为命中次数÷有效缓存查询次数，报出分母与窗口；Redis INFO的全局hits／misses不能直接当成某个接口的业务命中率。还要报告回源量、缓存内存、失效和一致性代价。
- **恢复语义如实记录**：当前失败重试由用户手动触发；启动恢复是把遗留running标记为failed／execution_interrupted，允许后续按规则重试，不是“自动重新生成成功”。分别统计中断状态正确收尾比例、实际发起重试后的成功比例，不能混成自动恢复率95%。
- **ai_job不是尝试账本**：当前行会随重试改写，不能仅靠最终快照算完整每次attempt成功率。测评时由运行脚本保留任务ID／attempt／事件时间／结果，再计算任务级与尝试级指标；是否新增持久化账本另行设计，不默认扩表。

工具先采用已有日志、MySQL及可复跑脚本，压力工具候选k6／JMeter，不因此安装新平台。k6 `http_req_duration`是发送、等待、接收阶段之和，不含初始连接等阶段；需要完整用户流程时另外计时并注明边界。

定义依据：[k6内置指标](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)、[MySQL 8.4 EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html)、[Redis INFO](https://redis.io/docs/latest/commands/info/)。2026-11-11核对，实施时固定实际工具版本；引用不代表已安装或运行。
