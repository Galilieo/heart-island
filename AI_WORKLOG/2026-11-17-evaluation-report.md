证据：`perf/results/b1/`（summary.json、{new,old}_requests.jsonl）、`perf/results/logs/java_old.log`。

### 2.2 假成功率（任务书 3.2）

每类故障 ≥20 次，内容标记逐请求注入；分母=注入且完成观测的请求数（全部 20/20）。
测量端：客户端 + 隔离库直查（旧版 `ai_reply.status` 与 `mood_record.ai_reply`；新版任务终态与公开回复）。

**旧版（2036e7af，同步链路）**

| 注入类型 | 日志误记成功 | 公开兜底文案 | 公开任意回复 | 保存 P50 |
| --- | ---: | ---: | ---: | ---: |
| 空正文（choices.content=""） | **20/20** | **20/20** | 20/20 | 1320ms |
| 纯空白（content="  "\\n\\t） | **20/20** | **20/20** | 20/20 | 1320ms |
| 截断 JSON（合法前缀截断） | 0/20 | **20/20** | 20/20 | 1319ms |
| 非法 JSON（不可解析） | 0/20 | **20/20** | 20/20 | 1321ms |
| HTTP 500 | 0/20 | **20/20** | 20/20 | 7ms |
| HTTP 429 | 0/20 | **20/20** | 20/20 | 7ms |
| 读超时（上游睡 50s） | 20/20* | 0/20 | 20/20 | **50031ms** |
| 对照（无故障） | 20/20（真成功） | 0/20 | 20/20 | 1321ms |

\\* 读超时行：旧版 RestTemplate **无读超时**，请求等满注入上限 50s 后拿到正常回复并记成功——
不是模型真的成功，而是“无超时上限 + 慢上游”下保存请求被无限拖住（50s 是注入设置的休眠上限，
不是产品行为上限）。若真实上游持续不响应，保存线程将一直等待。

结论（旧版）：**任何注入故障下保存都返回成功**；空正文/纯空白类还在日志层把兜底文案记成
`status=1` 的“成功”（无法与真成功区分）；截断/非法/HTTP 错误类日志诚实记 `status=0`，
但兜底文案照常公开写入用户日记。

**新版（eafc7cc，异步链路）**

| 注入类型 | 日志误记成功 | 公开任意回复 | 任务错误码（20/20 一致） |
| --- | ---: | ---: | --- |
| 空正文 | 0/20 | 0/20 | invalid_model_response |
| 纯空白 | 0/20 | 0/20 | invalid_model_response |
| 截断 JSON | 0/20 | 0/20 | provider_error |
| 非法 JSON | 0/20 | 0/20 | invalid_model_response |
| HTTP 500 | 0/20 | 0/20 | provider_error |
| HTTP 429 | 0/20 | 0/20 | provider_error |
| 读超时（上游睡 50s > Python 35s 读超时） | 0/20 | 0/20 | provider_timeout |
| 对照（无故障） | 20/20（真成功） | 20/20 | — |

结论（新版）：7 类注入全部如实 `failed`（错误码与 Python 服务 `ERROR_STATUS` 映射一一对应），
0 次公开兜底、0 次误记成功；保存确认不受故障影响（P50 5~9ms）。

仪器更正记录：首轮旧侧注入全部失效——旧版 RestTemplate 以 `Transfer-Encoding: chunked`
发送请求体，合成上游最初只按 Content-Length 读体，故障标记从未生效（对照组合 1320ms 正常
回复暴露了问题）。已修复合成上游支持 chunked 并重建旧侧隔离库重跑；首轮旧侧数据作废，
新版数据不受影响（经 Python httpx 转发为带 Content-Length 的常规请求）。
证据：`perf/results/b2/`（records.jsonl、summary.json）、探针转储 `/tmp/old_java_request.bin`。

### 2.3 三槽吞吐与排队（任务书 3.3）

开环定速到达（30/60/120/240 每分钟，各 5 分钟，共 3450 个任务），每档 30 个合成用户轮转；
**限流额度为本项单独调高**（mood 100000/时、1000000/日、global 100000/时，启动环境变量覆盖，
与产品默认的差异以此注明）；排队上限 100 全局 / 每用户活跃 3 为产品常量未动。
另设证据档 E240x300ms：到达同 240/分但上游延迟改 300ms，用于瓶颈归因。
测量端：客户端（保存确认）+ 上游日志毫秒级时间戳（排队=上游收到时刻−保存完成时刻；执行=上游耗时）
+ 每秒采样 ai_job 状态计数与进程资源。分母完整：HTTP 错误 0、客户端错误 0。

| 档 | 发送 | 任务终态 | 完成率 | 排队 P50/P95 | 执行 P50 | 队列深度峰值 | 保存确认 P95 |
| --- | ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 30/分 | 150 | 150 成功 | =到达（30/分） | 525/976ms | 1304ms | 2 | 19ms |
| 60/分 | 300 | 300 成功 | =到达（60/分） | 510/965ms | 1304ms | 3 | 13ms |
| 120/分 | 600 | 524 成功 / 76 容量拒绝 | ~105/分 | 44.1/57.5**s** | 1304ms | 90 | 11ms |
| 240/分 | 1200 | 534 成功 / 666 容量拒绝 | ~107/分 | 54.0/58.5**s** | 1305ms | 90 | 10ms |
| 240/分＋上游300ms | 1200 | 972 成功 / 228 容量拒绝 | ~194/分 | 24.8/29.2s | 305ms | 90 | 9ms |

每分钟完成数=成功任务÷5 分钟发送窗（含少量收尾排空；逐分钟分布见 results/b3/summary.json）。

**瓶颈证据链**：
1. 上游 1300ms 档的首要瓶颈是**上游延迟 × 3 槽**：服务率上限 = 3 ÷（上游 1.31s + 每任务
   固定开销 ~0.4s：领取/提交事务与 1s 扫描粒度）≈ 105~107 任务/分；L120 与 L240 完成率相同
   （都已饱和），排队增长符合 Little 定律：在制 90 ÷ 1.75 任务/s ≈ 51s ≈ 实测排队 P50 54s（L240）。
2. 上游 300ms 证据档：完成率 106→194/分（1.8 倍）——上游延迟确为 1300ms 档的首位瓶颈；
   但 194/分**低于理论值 ~257/分**（3 ÷ 0.705s/任务），缺口正是每任务 ~0.4s 固定开销开始显现，
   同时 Java CPU（ps 生命周期平均口径，非瞬时）达 91.6%——**继续压缩上游延迟，每任务开销与
   Java CPU 将成为下一层瓶颈**，不能据此说瓶颈“与 DB/Java 无关”。
3. **容量拒绝由每用户活跃上限先触发**：30 用户 × 3 = 90，实测队列深度峰值恒为 90，全局排队
   上限 100 从未触及；被拒任务保存时即 failed(capacity_exceeded)，保存确认不受影响（P95 ≤19ms）。
4. 资源：Java RSS 215~362MB；DB 连接数恒为 Hikari 池上限 10（含空闲，非繁忙证据）；
   Python 服务以 3 并发等待为主（CPU 采样取到 uv 包装进程为 0%，口径缺陷如实注明）。

结论：三槽在 1300ms 上游下稳定服务 ~105 任务/分，瓶颈=上游延迟×槽位；到达超过服务率时排队
线性增长至每用户活跃上限即开始背压拒绝，保存路径始终快速返回。上游提速到 300ms 后完成率
194/分仍低于 257/分理论值，~0.4s/任务的编排开销与 Java CPU 开始显现为下一层瓶颈——后续若要
继续提吞吐，方向在扫描粒度/事务开销/槽位数，而不是再压上游延迟。排队时长上限实际由在制上限
（用户数×3）决定——这是把等待显式化并加背压的设计结果，不是事故。

证据：perf/results/b3/（summary.json、各档 requests.jsonl 与每秒采样）。

### 3.1 并发写入（任务书 4.1）

已有证据引用：`AiJobPersistenceIT`（真实 MySQL 独立连接的锁等待与两种提交顺序，测试代码内固定证据）。
本任务补充的黑盒顺序矩阵（`perf/run_c1.py`）：**6 场景 × 50 轮 = 300 轮，观察到 0 次错误写入**
（只声明上述场景与轮数，不外推所有并发时序）。时点控制用内容标记 `#FAULT:hold#` 挂起上游，
保证「修改/软删」确实发生在生成中；每轮以数据库终态 + 上游调用计数取证。

| 场景（先后顺序） | n | 预期与观察 |
| --- | ---: | --- |
| S1 修改在生成中 → complete | 50 | 旧任务 superseded 50/50，新版本由新任务成功后才可见回复 50/50 |
| S2 完成后修改 | 50 | v1 成功合法；修改产生 v2+新任务，旧回复不覆盖新版本 50/50 |
| S3 软删在生成中 → complete | 50 | 任务 superseded、已删记录 ai_reply 保持 NULL、详情不再返回 50/50 |
| S4 完成后软删 | 50 | 回复先合法写入，软删后详情不返回 50/50 |
| S5 失败任务 retry vs 修改 | 50 | retry 409「回应任务已失效」50/50；旧任务转 superseded（attempt 不变）；旧任务无再次上游调用；新版本任务正常成功 |
| S6 失败任务 retry vs 软删 | 50 | retry 被拒 50/50；旧任务 superseded；无再次上游调用 |

行为语义备注（设计如此，非缺陷）：版本推进或删除会把旧版本的未完成/**已失败**任务统一转
`superseded`（保留 last_error_code，attempt_count 不变）——旧任务不可再被 retry，靠新版本的新任务
重新生成；任务查询 API 对过期任务按设计返回 409（`回应任务已失效`）。

测量更正记录：首轮 S1/S3 全部误报（脚本断言用了任务查询 API——过期任务 API 返回 409 data=null，
无法观察终态；另有 mysql --batch 的 NULL 字面量被当成已写回复），二轮 S5/S6 预期写错
（要求旧任务保持 failed，实际设计为 superseded）且 S5 把新版本任务的合法调用误计为重复执行。
三轮修正后全部通过；产品三轮行为一致（首轮的 DB 终态即正确），更正全部记录在案。

证据：perf/results/c1/（records.jsonl、summary.json）。

### 3.2 重启恢复（任务书 4.2）

真实 `kill -9` Java 进程后重启（SmartLifecycle 启动时 `recoverInterrupted`），三时点各 10 次，
每轮按上游日志证据归类（不凭时序猜测）。断言：全局遗留 running=0、本任务
failed/execution_interrupted、重启后无新上游调用、mood_record.ai_reply 保持 NULL、无 ai_reply 日志行。

| 时点 | 证据定义 | n | 正确收尾 | 重复执行 | 关键观察 |
| --- | --- | ---: | ---: | ---: | --- |
| P1 领取后（上游未收到） | kill 时刻上游日志无该任务条目（先 SIGSTOP uvicorn 保证） | 10 | 10/10 | 0 | 9/10 解冻后出现恰好 1 次“孤儿调用”（冻结期积压的请求被处理，Java 已死，无副作用）；1/10 连孤儿调用也没有 |
| P2 生成中 | `#FAULT:hold#` 挂起，上游日志出现 held 后 kill | 10 | 10/10 | 0 | 释放后响应流向已死连接，无副作用 |
| P3 完成前 | `#FAULT:slow_body#` 响应头已发、正文分块慢发中 kill | 10 | 10/10 | 0 | **10/10 上游把正文完整发完（slow_body_finished）**——供应商侧已完成生成，而数据库只有 execution_interrupted、无回复写入 |

结论：三时点共 30 次，全部被启动恢复正确标为 `execution_interrupted`（不是自动重新生成）；
无遗留 running、无重复执行、无错误写入。P3 直接演示了任务书要求写明的边界：**数据库状态不能
说明供应商侧是否已经执行或计费**——上游已完整产出响应，数据库只能如实记录“未确认”。

时点与仪器说明：P1 的“上游未收到”由冻结 Python 服务保证（kill 时上游日志 0 条，按证据归类，
不依赖毫秒级竞速）；P3 首轮分块间隔 1s 超过 Python 40s 时限导致正文未发完，二轮调 300ms 补齐
“已发完”证据，两轮各 10 次收尾行为一致；脚本 counters 的口径瑕疵（条目数 vs 唯一时间戳、
两轮共用标记）已核对原始日志修正，不影响断言。

证据：perf/results/c2/（records.jsonl、summary.json）、perf/results/fake_upstream.log。

## 5 发现（不修，按任务书第 9 节只记录）

- **F0（执行事故，非产品问题）**：建隔离库时 `sql/xinyu.sql` 开头 `USE xinyu` 把管道执行切到
  业务库，DROP 了 7 张表（favorite/post_like/community_reply/community_post/topic/ai_reply/mood_record）。
  已按同提交结构重建；`user`（1 行）与 `ai_job`（2 行）数据完好。**经用户核对 binlog 更正：
  这 7 张表在本次删除（11-17 12:37）之前已经是空表**（11-16 20:07 之后 `xinyu` 库只有 user 表
  有写入），本次没有丢失行数据；真正的清空发生在 11-16 20:05～20:07（与
  `xinyu_test_browser_20261116` 同时段），与本任务无关。如需恢复由用户另行决定，不在本任务范围。
  防复发：`perf/lib.py` 建库前剥离 `USE`/`CREATE DATABASE` 并断言库名前缀。
- **F1（旧版，产品行为）**：上游任何异常（含连接错误、HTTP 4xx/5xx、非法响应）都被
  `catch(Exception)` 吃掉，写兜底文案到 `mood_record.ai_reply` 并返回保存成功；B1 中在并发
  连接异常下自然出现（c10 时 14/200=7%），B2 受控矩阵见 2.2。空正文/纯空白时旧版
  `parseReply` 返回兜底文案且**记 success=1**（日志层面无法区分真成功）。
- **F2（旧版，产品行为）**：RestTemplate 无连接/读超时，慢上游下保存请求无限等待
  （B2 读超时注入实测：等满 50s 注释上限后按成功返回）。
- **F3（仪器限制）**：JDK HttpURLConnection keep-alive 与 Python `http.server`（合成上游）
  在并发下出现 Connection reset / Unexpected EOF（B1 旧侧 72 次）；加大 listen backlog
  (256) 后仍存在。不影响本报告百分位结论（污染样本在 min 端），复跑者如需完全消除可改用
  真 HTTP 服务实现。
- **F4（产品观察，旧版）**：RestTemplate 对含中文的 JSON 请求体一律使用
  `Transfer-Encoding: chunked`（B2 探针抓包证实）——多数供应商兼容，但自建/严格网关可能拒绝；
  也提醒自建测试桩必须支持 chunked（首轮 B2 旧侧注入失效的根因）。
- **F5（产品观察，新版 API 语义）**：任务查询 API 对过期任务（来源版本推进或已删除）按设计返回
  409「回应任务已失效，请刷新记录」；前端轮询旧任务在用户编辑/删除后会遇到该响应，需按
  “刷新记录”处理而不是无限重试（本轮测试脚本首轮即被此语义绊倒，前端接入时同样要注意）。
- **F6（产品观察，新版）**：版本推进/删除会把旧版本**已失败**任务统一转 `superseded`
  （保留 last_error_code、attempt 不变、不可再 retry）——与「失败任务可手动重试」的直觉有边界：
  只有当前版本的失败任务可重试。属设计语义，建议在功能契约中已覆盖的前提下，前端提示文案区分
  “已过期”与“失败可重试”。
- **F7（测量方法备忘）**：`ps -o pcpu` 为进程生命周期平均而非瞬时值（B3 Java CPU 数字只能作
  方向性提示）；`mysql --batch` 将 NULL 输出为字面量 `"NULL"`（已在本轮脚本统一还原）；
  `uv run --directory` 会切换 cwd，子进程相对路径需用绝对路径。
