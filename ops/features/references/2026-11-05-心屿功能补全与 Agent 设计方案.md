# 心屿功能补全与 Agent 设计方案

Nov 4, 2026 · @Galilieo

## 总览

结论：心屿以作品展示为主，服务于 Agent 开发方向的求职，但按真实产品的成熟度来设计。AI 部分沿用 agent-lab 已定的方向，拆成 Java 业务后端 + Python AI 服务，分 5 个阶段推进，合计约 12–14 周。本文的设计比实际要做的多，每项都标了“必做 / 推荐 / 可选”，后面按时间酌情实现。

- **现状**：主流程完整，分层清晰；底部导航、路由懒加载、401 状态码都已修好。`ops/features/` 里有多轮对话、长期记忆、情绪周报、RAG、工具调用 5 份初版规划，均未实现。
- **必须先解决的 3 个问题**：AI 回复链路没有任何自伤或危机识别；调用 DeepSeek 的 `RestTemplate` 没有设置超时，且在新增心情的请求里同步执行；社区没有举报、屏蔽和敏感词过滤。
- **AI 架构**：Java 保留登录、权限和业务数据；Python 服务从 agent-lab 迁入，负责模型调用、Agent 编排、记忆、RAG 和评测。这与 agent-lab 路线第 11 阶段的决定一致，迁移顺序也沿用那里的安排。
- **展示重点**：Agent 岗位面试看的不只是“能聊天”，更看安全边界、工具权限、记忆可控、评测和可观测。本方案把这些当作一等公民来设计，见“Agent 工程成熟度设计”一节。
- **底线**：以作品展示为主，也不能省掉危机识别，因为只要有人真的在上面写心情，这条就必须做。可以用邀请码注册或演示账号控制真实用户规模，降低运营和合规压力。

本文基于 2026-11-02 的提交 `060a042`（fix(auth): 统一登录与权限校验的 HTTP 状态码）阅读源码得出，涉及线上环境的部分未实测。

## 现状盘点

功能骨架都在，缺的是每个模块的“第二层”：安全、回看、治理和留存。

| 模块 | 已有 | 缺口 | 优先级 |
| --- | --- | --- | --- |
| AI 回复 | 心情和帖子单次回复、失败兜底、调用日志、可关闭 | 危机识别、超时、异步、限流、多轮对话、记忆 | P0（危机、超时） |
| 社区 | 话题、发帖回复、点赞收藏、最新/热门、帖子 AI 回复 | 举报、拉黑、敏感词过滤、通知、触发警告 | P0（举报、过滤） |
| 账号 | 用户名密码注册、JWT、资料、改密、个人统计 | 隐私政策与用户协议、注销、数据导出、找回密码、手机号或微信登录 | P0（协议、注销） |
| 后台 | 用户、帖子、回复、话题、AI 记录、概览 | 举报处理队列、风险事件列表、AI 记录脱敏 | P0 |
| 心情记录 | 6 种固定心情、增删改查、类型和日期筛选、近 7 天趋势 | 标签、强度、月历、关键词搜索、草稿、提醒、周报 | P1 |
| 工程 | 自建设计系统、底部导航、懒加载、统一 401 | AI 异步化、SSE、监控告警、PWA | P1 |

两处具体代码问题：

- `config/RestTemplateConfig.java` 直接 `new RestTemplate()`，没有连接和读取超时。DeepSeek 一旦卡住，`/mood/add` 会一直挂着，还会占住 Tomcat 线程。
- `ai_reply.prompt` 保存了完整的日记原文，后台“AI 记录”页可以直接看到。用户写的是很私密的内容，这里需要脱敏或分级查看。

## P0 安全与合规底线

这 6 项在任何新功能之前完成，约 2 周；其中危机识别最重要，因为现在的 prompt 遇到轻生表达时，模型只会回一段温柔的话。

1. **危机识别**
   - 新增 `RiskCheckService`，在所有 AI 调用之前执行：关键词规则（高召回）+ 一次低成本分类调用，输出 `NONE` / `LOW` / `HIGH`。
   - `HIGH` 不进普通生成，返回固定模板：表达关心、给出求助热线、建议联系身边信任的人。前端用醒目但不吓人的卡片展示，并写入 `risk_event`。
   - 心情、帖子、社区回复和以后的 agent 对话共用这一个入口，不让模型自己决定要不要“触发危机流程”。
   - 热线放在配置文件里，上线前核对号码，例如全国心理援助热线 12356、北京心理危机研究与干预中心 010-82951332。
   - 社区帖子判为 `HIGH`：仍可发布但默认折叠，后台高亮。是否由管理员私信关怀，v1 先不做。
2. **AI 超时、异步与限流**
   - `RestTemplate` 设置连接超时 3 秒、读取超时 20 秒。
   - 心情先落库并立即返回，AI 回复用 `@Async` 生成后写回；前端先轮询，阶段 4 换成 SSE。
   - 按用户限流（内存令牌桶即可，以后再上 Redis），防止刷接口耗光 API 额度。
3. **内容安全**：帖子、回复和 AI 输出都要过一遍。作品展示阶段可以先用本地敏感词库加风险分级；开放公开注册前，再接阿里云、网易易盾或数美等云服务。
4. **举报**：帖子和回复加举报按钮，新增 `content_report` 表和后台处理队列，处理结果通知举报人。
5. **AI 记录隐私**：后台列表只显示业务类型、状态和错误信息；查看原文需要点开，并记录谁在什么时候看过。更彻底的做法是不存 prompt 原文，只存模板版本号。
6. **账号合规**：注册时勾选隐私政策和用户协议；注销账号（软删除，30 天后物理删除）；导出我的数据（JSON）。另外请确认线上的 test 管理员账号已经处理。

## 日记核心功能补全

目标是让用户“写得下去、翻得回来”，同时为 agent 准备结构化数据；约 2–3 周。

| 功能 | 做法 | 改动范围 |

| 标签 | 预置工作、学业、家人、朋友、感情、睡眠、身体，另可自定义 | 新表 `mood_tag`、`mood_record_tag`；`MoodForm` 加标签选择 |
| 心情强度 | 1–5 分，选填 | `mood_record` 加 `intensity` 字段；趋势图可以画强度，不只是计数 |

## 社区治理与留存

以作品展示、Agent 岗位为目标时，这一组整体是**可选**的（举报除外，它在 P0 里），可以放在 AI 阶段之间穿插，约 2 周。如果时间有限，优先做“站内通知”和“温和回应”，最能体现产品感。

- **拉黑与屏蔽**：拉黑某个用户后双方互相看不到内容；支持屏蔽关键词。新表 `user_block`，唯一约束 `user_id + blocked_user_id`。
- **温和回应**：把点赞扩展为“抱抱 / 我也是 / 加油”。`post_like` 加 `reaction_type` 字段，旧数据默认“抱抱”，接口向后兼容。
- **楼主控制**：可以关闭评论，可以隐藏别人在自己帖子下的回复。
- **触发警告**：发帖时可勾选“内容较沉重”；风险分级为 `LOW` / `HIGH` 时自动折叠，读者点开才看。
- **站内通知**：有人回复、回应，或举报处理完成时通知。新表 `notification`，顶部小红点，v1 用轮询。
- **帖子内匿名名**：现在所有人都显示“匿名岛民”，同一帖子下分不清谁在和谁说话。可以为每个用户在每个帖子下生成稳定的随机名（如“海风岛民”），帖内一致、跨帖不同，楼主标“岛主”。

## 文案与 AI 语气

界面文案整体朴素，问题不大；“AI 味”主要来自 AI 回复本身。现在的 prompt 让每条回复都是“先接住情绪，再给一句小建议”，长度固定在 60–100 字，用户记到第三条就能看出套路。这一项改动小、见效快，建议放进阶段 1，和危机识别一起改 `AiReplyService`，约半天到一天。

### AI 回复 prompt

1. **长度跟着用户走**：用户写一句，就回一两句；写一大段，才多回一些，上限 100 字。
2. **不固定结构**：可以只回应一个细节，可以只问一个具体的问题，不必每次都给建议。prompt 里明确写出“不需要每次都给建议”。
3. **必须提到具体内容**：回应用户写到的人、事或细节，不说换一篇日记也成立的话。
4. **开心就跟着开心**：记录是“开心”时不要转去安慰，也不要提醒“也要照顾好自己”。
5. **禁用词表**：接住、此刻、抱抱你、你并不孤单、允许自己、辛苦了、一切都会好起来、慢慢来、给自己一点时间、你已经做得很好了。写进 prompt，同时在评测里统计命中率。
6. **人工写的示例**：放 2–3 条结构不同的好回复作为 few-shot，比再加形容词有效。
7. **社区回复直接称“你”**：现在的“这位朋友”“写下这段话的人”反而更像机器。

去掉 AI 腔不等于隐藏 AI 身份：“AI 生成”的标识照常保留，也不能让它说“我也经历过”这类假装是人的话。

下面这段可以替换 `buildMessages` 里的 system 内容，作为起点：

```text
你是心屿，用户写心情日记时偶尔回一句话的朋友。
- 回复长度和用户差不多：对方写一句，你就回一两句；最多 100 字。
- 一定要提到对方写的具体的人、事或细节。
- 不需要每次都给建议。可以只回应一个细节，也可以只问一个具体的问题。
- 对方开心时就跟着开心，不要转去安慰。
- 不诊断，不给医疗建议，不说教，不用“必须”“应该”。
- 不要使用这些说法：接住、此刻、抱抱你、你并不孤单、允许自己、辛苦了、一切都会好起来、慢慢来、给自己一点时间、你已经做得很好了。
- 不要假装自己是人，不说“我也经历过”。
- 只输出回复正文，不用列表和表情符号。
```

示意对比（不是线上实际输出）：用户写“今天面试又挂了，第三家了。”套路化的回复会先说“面试接连受挫一定很难受”，再建议“给自己一点时间休息”；改后更接近“第三家了，确实磨人。这次是挂在哪一轮？”

**验证**：准备约 20 条自己写或脱敏后的日记样例，新旧 prompt 各跑一次，打乱顺序后盲看对比；再统计禁用词命中率，以及回复以建议结尾的比例。这批样例直接并入“固定评测集”。

## Agent「守岛人」设计

守岛人把 `ops/features/` 里的 5 份规划串成一条可控链路，定位是陪用户整理情绪的同伴，不做诊断、不做治疗。

&#91;embedded content: 守岛人处理链路 · 9 个环节\]

只有判为 NONE 或 LOW 的消息才会进入 agent 循环；工具调用都经过后端白名单校验，记忆只在会话结束后异步写入。

### 服务拆分：Java + Python

agent-lab 路线第 11 阶段已经定下：Java 保留业务、登录与权限，Python 承接模型调用、Agent 编排、记忆和 RAG。下面是落到心屿时的具体契约。

&#91;embedded content: 服务拆分 · Java 与 Python 的职责和数据归属\]

- **入口只有 Java**：浏览器只和 Java 通信。Java 校验 JWT、跑风险分级，再带着委托令牌调用 Python；SSE 也由 Java 转发。代价是多一层转发，好处是鉴权、限流和审计只有一处。
- **委托令牌**：Java 每次调用 Python 时签发短期令牌（HMAC 签名，含 user\_id、会话 id、5 分钟过期）。Python 调工具时把令牌原样带回 `/internal/agent/*`，Java 再校验一次归属；Python 不信任任何参数里的 user\_id。
- **数据归属**：业务数据留在 `xinyu` 库；会话、消息、记忆、工具日志、周报放在同一 MySQL 实例的 `xinyu_ai` 库，由 Python 管理迁移，不沿用 agent-lab 的 SQLite。向量库只放知识库，用户日记不进向量库，注销时也就不用清理向量。
- **注销与导出**：Java 的注销、导出接口同时调用 Python 的删除和导出接口，两边都完成才算成功。
- **降级**：Python 不可用或超时时，Java 回退到现有的单次 AI 回复，聊天入口提示“守岛人暂时休息”；嵌入服务不可用时只关闭检索工具，对话照常。
- **嵌入模型**：agent-lab 用本机 Ollama 跑 BGE-M3。服务器内存不够的话，可以换云端嵌入接口，只要接口层保持一致即可。

### 每一层做什么

1. **风险分级**：复用 P0 的 `RiskCheckService`。`HIGH` 直接返回危机模板，不进入 agent 循环。
2. **上下文组装**：系统 prompt + 会话最近 10 轮 + 更早消息的摘要 + 已开启的长期记忆（最多 10 条）+ 关联的心情记录。
3. **Agent 循环**：先复用 agent-lab 的原生循环（已有模型调用次数上限和中途失败边界），学完 LangGraph 后改为状态图：模型节点、工具节点、条件边，最多 4 轮工具调用，超出就基于已有结果作答。每次调用写 `ai_tool_call_log`。
4. **输出**：内容安全过滤 → SSE 流式返回。失败时保留用户消息，AI 消息标记失败并提供重试。
5. **会话结束后**（30 分钟无新消息）异步：更新会话摘要、抽取候选记忆。

### 工具白名单

`userId` 一律由后端从登录上下文注入，不出现在工具参数里，模型无法读到别人的数据。

| 工具 | 用途 | 类型 | 校验 |
| --- | --- | --- | --- |
| `get_mood_stats(range)` | 7/30/90 天的心情分布、平均强度、常见标签 | 只读 | `range` 只接受枚举值 |
| `query_moods(from, to, moodType?, tag?)` | 读具体记录原文，最多 10 条 | 只读 | 时间跨度不超过 90 天 |
| `get_weekly_report(week)` | 读已生成的周报 | 只读 | 只能读自己的 |
| `search_memory(keyword)` | 查长期记忆 | 只读 | 记忆开关关闭时不注册此工具 |
| `get_exercise(type)` | 呼吸练习、5-4-3-2-1 着陆、写下担心等 | 只读 | 内容来自人工审核过的知识库 |
| `draft_mood_entry(...)` | 把对话整理成一篇心情草稿 | 写，需确认 | 只返回草稿，用户点“保存”才调用 `/mood/add` |

不提供的工具：读取社区他人内容、发帖、修改资料、任何外部网络请求。

### 长期记忆

- 按 `mood-memory-v1.md` 执行，并以 agent-lab 的 Memory V1.1 为基础：user / conversation 两级范围，Core 记忆默认注入，Regular 记忆按问题选择。默认关闭，由用户主动开启。
- 只记用户明确说过的稳定事实，如“在准备考研”“和室友关系紧张”“散步能让我放松”；不记模型推断、诊断式结论和自伤相关内容。
- 新增“岛屿记忆”页：列表、来源、删除和总开关；关闭后 prompt 不再读取任何记忆。

### 入口与界面

- 心情详情的 AI 回复下方加“继续聊聊”，带着这条记录开新会话；这是最自然的入口。
- 独立入口可放在“心情”页顶部，或底部导航加第 5 个 Tab，看试用反馈再定。
- 调用工具时显示轻提示，例如“正在看你最近 30 天的记录”。
- 每条 AI 消息标注“AI 生成”，满足《人工智能生成合成内容标识办法》的显式标识要求。

### 模型与成本

- 对话、风险分类、记忆抽取都用现有的 `deepseek-v4-flash`，关闭 thinking；周报可以换更强的模型。
- 设每人每日对话上限，后台概览增加 token 用量统计。
- 面向大陆公众提供生成式 AI 对话，可能需要做生成式人工智能服务登记或备案。只开放邀请码注册、以作品展示为主时压力会小很多；开放公众注册前，请找熟悉当地规定的人确认。

## Agent 工程成熟度设计

这一节是面向 Agent 岗位的“设计储备”：17 项里 5 项必做，其余按时间挑选，每一项都对应面试中常被追问的一个问题。分级可以直接在表里改。

| 设计项 | 展示的能力 | 分级 | 阶段 |
| --- | --- | --- | --- |
| 危机识别与固定流程 | 安全护栏：高风险不交给模型判断 | 必做 | 1 |
| 工具白名单 + 委托令牌 | 权限设计：模型拿不到别人的数据 | 必做 | 4 |
| 全链路 trace | 可观测：一个 trace\_id 串起 Java 请求、模型调用、工具调用、耗时和 token | 必做 | 3 |
| 降级与超时策略 | 韧性：Python、模型、嵌入任一不可用时都有明确表现 | 必做 | 3 |
| 固定评测集 + 回归脚本 | 评测：陪伴质量、危机识别、工具选择、越权与注入各一组用例，改动前后可对比 | 必做 | 4–5 |
| SSE 流式与用户中断 | 流式：真流式，断开后停止生成并保存已生成部分 | 推荐 | 4 |
| LangGraph 状态图 + checkpoint | 编排：能画出状态图，进程重启后会话可恢复 | 推荐 | 4 |
| 人工确认节点 | HITL：草拟日记在保存前暂停，等用户确认 | 推荐 | 4 |
| 提示注入防护 | 安全：日记原文作为数据放进隔离标签，其中的指令不执行；评测集放注入样例 | 推荐 | 4 |
| 情绪周报定时生成 | 后台任务：每周批量生成，失败可重试，不重复生成 | 推荐 | 4 |
| Prompt 版本化 | 工程化：模板带版本号，日志记录版本，改版本必跑评测 | 推荐 | 3 |
| 分层记忆 + 可管理 | 记忆：Memory V1.1 迁入，用户可查看、删除、关闭 | 推荐 | 5 |
| 知识库 RAG + 引用校验 | RAG：复用 agent-lab 的 rag\_citations，练习内容带来源 | 推荐 | 5 |
| 成本与配额面板 | 运维：每用户每日上限，按模型拆分 token 用量 | 可选 | 5 |
| LLM 评审自动打分 | 评测扩展：更强的模型按评分表打分，和人工抽检对照 | 可选 | 5 |
| MCP Server 暴露只读工具 | 协议：把心屿工具以 MCP 提供，可接入其他客户端 | 可选 | 5 |
| 模型路由 | 成本：对话用 flash，周报用更强的模型 | 可选 | 5 |

不建议为了展示做多 Agent：心屿的任务链很短，多 Agent 只会增加延迟和失败点。面试时讲清楚为什么不做，比硬做更有说服力。

做完的每一项，建议在 README 里留一条“设计取舍 + 验证证据”，延续 agent-lab 记录 RED/GREEN 和测试基线的习惯；只写已验证的部分。

## 分阶段推进计划

&#91;embedded content: 推进路线 · 5 个阶段及各自的放行条件\]

阶段 1 不能跳过。阶段 3 起的 AI 部分跟着 agent-lab 的进度走，迁移顺序基本沿用其路线第 11 阶段（调用日志 → 非流式多轮 → 业务上下文 → SSE → RAG → 查询型工具）。唯一调整是把查询型工具提前到阶段 4，因为守岛人的回顾能力依赖它；RAG 只用于练习知识库，放到阶段 5。社区功能是可选项，可以在 AI 阶段之间穿插。

### 推进方式

- 沿用两个仓库的工作方式：心屿按 `AGENTS.md` 先在 `ops/features/` 写设计文档再改代码；AI 能力先在 agent-lab 用测试验证，再整理成 xinyu-ai 的服务接口。
- 需要新写的设计文档：`risk-check-v1`、`content-report-v1`、`account-compliance-v1`、`mood-tag-v1`、`ai-service-split-v1`、`agent-orchestration-v1`、`agent-eval-v1`；社区相关的 `community-governance-v1` 可选。
- 每个阶段结束都发布一次线上版本，不攒到最后一起上。
- 评测集从阶段 1 就开始积累：危机识别的正例和容易误判的反例（如“累死了”“想死你了”）先用于规则测试，阶段 4 再扩展到陪伴质量、工具选择和注入用例。
- 阶段 3 起，后台概览增加 AI 调用次数、失败率、平均耗时、token 用量和风险事件数。

### 需要先确认的问题

- [x] 定位：以作品展示为主、服务于 Agent 开发方向的求职，但按真实产品的成熟度设计。
- [ ] 注册是否改为邀请码？这决定内容安全服务和生成式 AI 备案要投入多少。
- [ ] 服务器内存能否跑 BGE-M3？不够就换云端嵌入接口。
- [ ] 移动端走 PWA 还是微信小程序？小程序要单独备案，但更贴近大陆用户的使用习惯。
- [ ] 守岛人的独立入口放“心情”页顶部还是底部导航？可以先找几位用户试用再定。
