### 推荐顺序

1. **1a 完成后**：心情回应评测集＋危机识别评测＋L3 SQL 报告。
2. **阶段 2**：周报数字一致率与引用忠实度（有客观标准答案，最适合评测）。
3. **阶段 4、5**：Agent 工具评测、记忆与 RAG 评测。

### 原则

- 评测集只用**合成数据**，不使用真实用户日记。
- 每次改 prompt 或换模型都重跑，记录 `template_version` 与前后指标。
- LLM 评审先与 20～30 条人工标注对齐，一致率达标后再大规模使用。
- 能用业界标准指标的用标准名；产品特有的项（语气、危机）用 G-Eval 自定义评分标准。

## 5. 危机识别：混淆矩阵

- **TP**：该抓且抓到；**FP**：不该抓却抓到；**FN**：该抓没抓到；**TN**：不该抓也没抓。
- 精确率 = TP ÷ (TP + FP)；召回率 = TP ÷ (TP + FN)；F1 = 2 × 精确率 × 召回率 ÷ (精确率 + 召回率)。

| 层 | TP | FP | FN | TN | 精确率 | 召回率 | F1 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 正则层（固定 SUPPORT） | | | | | | | |
| 模型层（prompt 安全段，仅统计正则未命中的样本） | | | | | | | |
| 两层合计（任一识别） | | | | | | | |
| *示例（虚构）* | *12* | *1* | *3* | *34* | *92.3%* | *80.0%* | *85.7%* |

解读：精确率低说明误报多，普通句子也收到危机回应；召回率低说明漏判多，要依赖模型层兜底。**两层合计的召回率才是用户实际得到的保护。**

## 6. LLM 评审校准

1. 从评测集中抽 20～30 条，人工按评分标准打 1～5 分。
2. 用 LLM 评审对同样的样本打分。
3. 差值 ≤1 视为一致，计算一致率与平均差值。
4. 一致率低于目标（80%）时，先修改评分标准（写成明确的评测步骤，而不是笼统的「打分」），再重新校准。

| 吞吐（三并发） | 每分钟完成的任务数 | 个／分钟 | 高 | 15 | | 3E 压测时统计；受供应商速率限制影响 |

安全相关（危机识别、提示注入）见第 3、5 节。

### SQL 参考

```sql
-- P50 延迟（P95 把 0.5 改成 0.95）
WITH d AS (
  SELECT TIMESTAMPDIFF(SECOND, started_at, finished_at) AS s,
         PERCENT_RANK() OVER (ORDER BY TIMESTAMPDIFF(SECOND, started_at, finished_at)) AS pr
  FROM ai_job WHERE status = 'succeeded'
)
SELECT MIN(s) FROM d WHERE pr >= 0.5;

-- 失败率
SELECT SUM(status = 'failed') / COUNT(*)
FROM ai_job WHERE status IN ('succeeded', 'failed');

-- 超时占失败比例
SELECT SUM(last_error_code = 'provider_timeout') / COUNT(*)
FROM ai_job WHERE status = 'failed';

-- 失败分类分布
SELECT last_error_code, COUNT(*) AS n
FROM ai_job WHERE status = 'failed'
GROUP BY last_error_code ORDER BY n DESC;
```
