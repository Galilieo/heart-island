# 12 代码可读性与审查规范

更新：2026-11-10。适用于本仓新增与修改的 Java、Python、Vue 主体代码及测试。

目的：让用户能按调用顺序审查、学习代码，让评审能快速判断“这轮是否只改了可读性、有没有行为变化”。
边界：这是评审约定，不是自动格式器；不替代正确性、测试、契约和独立评审。当前不引入 checkstyle、pydocstyle 或新依赖，靠本文清单和评审执行。

## 1 优先级与原则

1. 契约与正确性 > 可读性 > 个人风格偏好。
2. 可读性整理默认行为不变：不改方法签名、返回结构、SQL、事务边界、锁顺序、错误码和状态语义；必须改行为时单独说明原因并补测试。
3. 小步、局部：不顺手全文件格式化，不跨模块重排；一个 diff 只承载一个目的，便于审查和回退。
4. 以调用顺序为主：先让主流程能从入口读到结果，再考虑抽象；抽象只在能消除真实重复或隔离复杂步骤时使用。
5. 不复杂化：不新加框架、枚举、基类或工具门禁；公共 API 才写完整 Javadoc/docstring，getter/setter 不逐条注释。

## 2 项目依据

沿用 `AGENTS.md` 的可读性要求、`ops/11-learning-collaboration.md` 的带读与验证流程，以及 `ops/10-backend-rules.md` 的分层职责。下列约定用于本项目，不宣称已通过外部风格工具认证。

## 3 硬性要求

### 3.1 按功能阶段分段

有多步骤或副作用的方法按“参数校验 → 状态读取 → 请求/对象构造 → 执行 → 结果处理 → 资源清理”分段，段间留空行；异步、并发方法再补线程说明。示例：`AiJobRuntime.start/stop`、`AiJobWorker.generate`。

### 3.2 一行一个独立语句

一行只写一个独立语句；`if`、循环的执行体展开，不写 `a(); b();` 或 `if (x == null) return null;`。

### 3.3 条件与异常不过载

- 长布尔条件拆成含义明确的局部变量或私有方法。
- 禁止嵌套三元；单层简单三元可用，超过一层改 `if` 或局部变量。
- 不同失败原因分开校验、分开命名；错误分类/消息提常量。
- 内部诊断要能定位失败环节；普通用户／公开接口不泄露正文、凭据、原始异常或堆栈。经鉴权的全站ADMIN诊断查看按功能契约执行，不将后台诊断误套为公开接口。

### 3.4 方法职责与主流程

- 方法名说清职责，主流程能顺着调用顺序读懂。
- 预算计算、协议解析、状态判断、生命周期等复杂步骤按职责拆成小方法。
- 不为缩短方法制造无意义的跳转、包装或抽象；超过约 80 行先审视职责，而不是机械拆分。

### 3.5 命名、常量、单位与来源

- 变量、方法、常量按业务含义命名，避免 `a`、`data2`、`tmp` 这类缩写。
- 时间值注明单位（`Nanos/Millis/Seconds`）；上限、阈值、超时用具名常量。
- 常量注释说明来源（契约章节、数据库列、跨端文件），不把初值或估算写成实测标准。

### 3.6 注释

- 使用规范中文，写职责、设计原因、前置条件和关键边界；不逐行翻译代码，不写聊天进度、计划或情绪。
- 公开类/方法说明职责与必要的输入／返回／异常边界；Java 用 Javadoc，Python 用 docstring。只补有助于调用方理解的标签，不机械填满模板。
- 异步与并发代码：说明执行线程、共享/独立状态、超时、取消、事务和关闭行为。
- 跨端契约：错误码、字段、状态映射在单点说明，并指向对应契约；不在多处复制。
- 注释与实现同步；不靠长注释弥补过密结构。

### 3.7 换行与空行

空行用来分组，不靠注释硬分段：

- 包/导入分组之间空一行；字段、构造器、方法之间空一行。
- 方法内按 3.1 的阶段留空行；同一阶段内的连续语句紧挨着，不逐句空行。
- 连续 guard clause 均展开执行体；连续校验一行一项，必要时按失败原因留空行。
- 方法开头、结尾不留空行；不连续留两个及以上空行。

判断标准：两行之间没有空行，它们就应属于同一个功能块，能一句话说出这块在做什么；说不出来，说明该按阶段拆开或补空行（反之，逐句空行则说明空行用多了）。

换行只在“一行读不完或需要语义分组”时使用：

- 方法参数超过 3～4 个或明显超宽时，每个参数一行，或按语义分组。
- 较长链式调用按步骤换行；长布尔条件按 `&&/||` 分组，短调用和简单条件保持紧凑。
- 注解、泛型、record 组件按现有风格折行，不强行对齐。
- SQL 字符串保留原始排版，不为行宽破坏语义；错误消息拼接同理。
- 短表达式不硬拆成多行，也不手工补空格对齐。
- **不为对齐、凑行宽或个人习惯乱换行**；短参数列表、短条件、短链式调用保持单行，相邻同类结构折行方式保持一致。

目标：扫一眼能看出“分了几段、走到哪一步、参数是什么”，而不是靠数行数。示例：`AiJobRuntime.start/stop` 的阶段之间留空行，`MoodRecordController` 的方法参数按行折开，`AiJobMapper` 的 SQL 保留原排版。

## 4 审查清单

1. 能否按调用顺序复述输入、状态、副作用、返回和异常由谁处理？
2. 锁、事务、线程切换、`await`/`close`、取消是否有注释和边界说明？
3. 长条件是否已拆成命名变量或方法？
4. 魔法数、字符串、错误码是否有具名常量并写明出处？
5. 跨端字段、状态、错误码是否有单点对应说明？
6. 公开 API 的参数/返回/异常是否覆盖？测试是否读得出“输入—替换层—断言”？
7. diff 是否只做可读性？行为变化是否单列并补了测试？
8. 是否有无关重排、全文件格式化或改签名/接口？
9. 新增注释是否与代码同步？新增抽象是否必要，还是增加了跳转？
10. 是否跑了基线/改后测试，未验证项是否如实标注？
11. 换行与空行是否只在语义/长度需要处使用（没有为对齐或习惯乱拆），且能让阶段、参数和调用链可扫读？是否存在无意义硬拆或连续多空行？

## 5 本仓示例

- 常量与来源：`AiJobService` 的排队/用户上限（契约第 8 节）；Python `MAX_*` 与请求头/正文上限（README「请求与结果」）。
- 长条件与职责：`AiJobRuntime.stop` 拆成 `beginStopping → awaitExecutionsAndHttp → awaitDatabaseAndScanner → markStopped`；`AiJobWorker` 抽出预算判断 `requireBudget/budgetLeftNanos`。
- 命名消歧：`MoodRecordService.nonBlank` 与 `AiJobService.hasVisibleText` 名字区分“trim 判空”和“Unicode 可见字符”。
- 注释边界：Mapper 方法 Javadoc 写清条件与返回；`MoodRecordVO`/`AiJobVO` 用类级 `@param` 说明 `aiReplyState`、`retryable`。
- 测试可读：`AiJobLifecycleTests` 的构造 helper 一行一句；`AiJobStateTests` 用显式 import 代替全限定名。
- 跨端映射：Python `ERROR_STATUS` 与 Java `AiServiceClient` 的错误码/状态映射各自集中，注释指向同一契约。

## 6 不要做

- 为抽象而抽象，或引入新依赖、新工具门禁。
- 顺手全文件格式化、跨模块重排、改签名/接口/错误码。
- 为对齐或习惯乱换行，或对无关行重排换行，导致 diff 噪声掩盖真实改动。
- 给 getter/setter、显而易见的赋值逐条写注释；逐行翻译代码。
- 把计划、进度、聊天内容或临时笔记写进源码注释。
- 用长注释掩盖过密结构，或只跑测试不做 diff 自查。
- 把“逻辑严谨、测试通过、行数少”当作可读性已经合格的证据。

## 7 执行流程

1. 先说明目标、范围、涉及文件、行为不变的边界和验证方式，等待确认再改业务代码。
2. 核对可复用的改前基线；行为修改先观察RED，纯结构调整运行相关回归。
3. 按小步改结构/命名/注释，不同时改行为；每步保持可编译。
4. 改后重跑相关测试，检查 `git diff --check` 和完整 diff。
5. 按第 4 节清单自查，再交付带读或评审；未验证范围如实标注。
6. 用户正在整理可读性时暂停该段带读，版本稳定后重新核对源码，再按调用顺序讲解。

## 8 豁免与边界

- SQL 字符串、协议常量、prompt 文案、第三方或生成代码按原文保留，不为折行破坏语义。
- 测试 fixture 和被大量断言的构造代码可适度简写，但断言与失败信息要能读懂。
- 长 Javadoc 句子不强制按行宽折行；行宽不优先于可读性。
- 没有工具门禁不等于不检查：清单项在评审记录中逐项确认。

## 9 维护

- 标准变化先改本文，再改代码；在本文记录日期和原因。
- 不在每次聊天轮次新增规范文件；相关决定写入本文件或既有 `AI_WORKLOG/` 记录。
